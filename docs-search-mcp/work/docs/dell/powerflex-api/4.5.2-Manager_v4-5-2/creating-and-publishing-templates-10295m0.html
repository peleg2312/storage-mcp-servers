Creating and publishing templates

Template structure overview

Creating and publishing templates requires an understanding of the format of template data. At a
high level, templates consist of:

  • A list of components (type ServiceTemplateComponent) representing the desired configuration for
    that component. Example components are node components, VMware cluster components, and
    PowerFlex cluster components.
  • Each component has a list of resources (type ServiceTemplateCategory) which can be thought of
    as categories of configuration data for that component. Example resources for node components are
    OS Settings, Hardware Settings, BIOS Settings and Network Settings.
  • Each resource has a list of parameters which are the individual settings inside the resource. Each
    parameter has an id, a value and a variety of metadata around allowed values for that parameter.

Component (ServiceTemplateComponent) structure

A sample ServiceTemplateComponent component with some less-important fields omitted is shown here:

{
  "id": "6fe60444-8dd6-40b6-9f84-5cbb097cd513",
  "componentID": "component-server-1",
  "name": "Hyperconverged",
  "type": "SERVER",
  "associatedComponents": {
    "entry": [
      {
        "key": "583d54ea-01cd-4a9a-b68a-92151d0100d7",
        "value": {
          "entry": [
            {
              "key": "name",
              "value": "PowerFlex Cluster"
            }
          ]
        }
      },
      {
        "key": "fa9c6d01-9942-4041-8690-c66727250f34",
        "value": {
          "entry": [
            {
              "key": "name",
              "value": "VMWare Cluster"
            }
          ]
        }
      }
    ]
  },
  "resources": [ ... omitted ... ]
  "instances": 3
}

The meaning of these fields is:

  • id is a unique value for the component within the template. The client must generate this value.
    It only has to be unique within this particular template, not globally.
  • componentID is the id of the default template component that this component was created from.
    The default template is a special template with id 1000 that defines the menu of components that
    new templates can be created from and defines the possible resources and parameters available to
    that component. This will be described in more detail in the section on creating templates.
  • name is a name for the component which is displayed in the UI.
  • type is the compoennt type which can be one of:
    • SERVER for node (server) components.
    • CLUSTER for VMware cluster components.
    • SCALEIO for PowerFlex cluster components.
  • associatedComponents is a map used to describe relations between the different template
    components. It should contain an entry key which has a list of key / value pairs. The key
    is the component id of the component it should be related to and the value is another entry
    map containing the name of that component. In the above example the Hyperconverged component is
    associated to a PowerFlex cluster and a VMware cluster component.
  • resources are the list of resources (described below).
  • instances is the number of hardware instances that this component describes. This is only
    relevant for node components and describes the number of servers to be used when the template
    is deployed as a service.

Resource (ServiceTemplateCategory) structure

A sample resource is:

{
  "id": "asm::cluster",
  "displayName": "Cluster Settings",
  "parameters": [ ... omitted .. ]
}

The fields are:

  • id is a unique id for this resource.
  • displayName is the name to display in the UI for this resource.
  • parameters is a list of parameters.

Parameter (ServiceTemplateSetting) structure

A sample parameter from a VMware cluster component (with some less-important fields omitted) is seen
below. The display of template data in the PowerFlex Manager UI is highly data-driven – meaning
that many of the parameters in the API are used to drive the UI display of the template and may
not be directly relevant from the perspective of an API client.

{
  "id": "$new$datacenter",
  "value": "PowerFlex",
  "type": "STRING",
  "displayName": "New datacenter name",
  "required": true,
  "requiredAtDeployment": true,
  "hideFromTemplate": false,
  "dependencies": [
    {
      "dependencyTarget": "datacenter",
      "dependencyValue": "$new$"
    }
  ],
  "toolTip": null,
  "readOnly": false,
  "generated": false,
  "maxLength": 256,
}

The meaning of these fields is:

  • id is a unique key for the parameter.
  • value specifies the value for this parameter. From the perspective of creating, updating and publishing
    templates via the REST API, this is the only parameter field that needs to be programatically
    updated with the desired value. All other fields are retrieved from existing templates, as described below.
  • type describes the type of data. Primarily this is used by the UI to determine how to render
    this parameter. For example STRING parameters are rendered as text boxes and ENUMERATED
    parameters are rendered as select boxes.
  • displayName is the name of the parameter that is displayed in the UI.
  • required indicates whether a value is required in order to publish the template.
  • requiredAtDeployment indicates whether a value is required to be filled out in order to create a service
    from the template. In other words, the value does not have to be specified to publish the template
    but it must be provided when deploying the template as a service.
  • hideFromTemplate is true if it is a hidden parameter that is not displayed in the UI.
  • dependencies is a list of dependencies that must be sastisfied in order for this parameter to
    be displayed in the UI. If the dependencies are not met then the value is not required even if
    the required value is true. In the above example this parameter is only applicable if the
    datacenter parameter is set to $new$.
  • toolTip is an optional tooltip string to display in the UI.
  • readOnly is true if the value cannot be changed.
  • generated is true if the value is generated by PowerFlex Manager and does not need to be
    specified by the client.
  • maxLength is the maximum length of the value.

Note that in some cases the value parameter field is a JSON-encoded string of a more complex data
type. Important examples of this are the NETWORKCONFIGURATION type, which is used for definining
node network interfaces and the networks that should reside on them, as well as
VDSSETTINGSCONFIGURATION, which is used to define the desired VMware VDS switch and portgroup
configuration.

Creating a template

The general procedure for creating a template is as follows.

Create the initial template payload

This can be done in a number of different ways:

  1. Retrieve the default template with GET /Api/V1/ServiceTemplate/1000. This is a special template
    that defines the menu of components that can be used on new templates. The desired components can
    be copied into the new template payload. For example, if you want to create a hyperconverged
    template (which consists of a node component, a VMware cluster component, and a PowerFlex cluster
    component), those components could be retrieved from the default template and used to build the
    new template payload. The following fields need to be modified before adding the default template
    components to the new template payload:
    • id should be set to a unique id.
    • componentID should be set to the default component id if it is null or left as is otherwise.
    • associatedComponents should be filled out as described in the component structure section.
    • instances should be set to the desired number of nodes for a node component.
    • Individual resource parameter values should be updated as desired.
  2. Retrieve an existing sample template or template with
    GET /Api/V1/ServiceTemplate?filter=eq,name,{template_name}. The components should then be
    modified as described in 1.

Create the template

The payload built in the previous step should be used to create the template with
POST /Api/V1/ServiceTemplate.

Refine the template

As a result of creating the template new parameter and parameter options may be added that did not
exist in the default template that are specific to the parameter values used to create the template.
As a result the API client must retrieve the newly created template, update any parameters that
are missing values or reporting errors and update the template with the modified payload with
PUT /Api/V1/ServiceTemplate/{id}.

Publish the template

To publish a template that is in draft state simply set the template draft parameter to true and
update it with PUT /Api/V1/ServiceTemplate/{id}.
