Working with the PowerFlex Installation Manager (IM) REST API

PowerFlex Installer is an orchestration engine that runs commands from different queues (nodes and MDM) at different phases, and labels them as a process such as an upgrade.

The PowerFlex gateway REST API begins with the /im/ prefix.

Asynchronous operation model

All /im/ operations act on the entire cluster and may take significant time to complete, especially on large clusters. These operations follow an asynchronous pattern:

Operation flow:

  1. Initiate Operation - Call the operation endpoint (e.g., /install, /upgrade)
    Returns immediately with HTTP 202 Accepted
  2. Monitor Progress - Use polling APIs to check operation status
  • Poll the status endpoint at regular intervals
  • The operation status provides information such as the number of completed commands, currently running commands, and failed commands.
  1. Completion or Abort - When finished or to cancel the operation
  • Use cleanup APIs to finalize or abort the operation
  • Retrieve final results or error information

The following are the list of polling and control APIs:

  • GET /im/types/ProcessPhase/actions/queryPhaseState: Check the current state of the operation phase
  • POST /im/types/ProcessPhase/actions/moveToNextPhase: Advance to the next phase (when current phase is complete)
  • POST /im/types/ProcessPhase/actions/moveToIdlePhase: End the operation (move to idle state)
  • GET /im/types/Command/instances: List all commands and their states
  • GET /im/types/Command/instances/actions/queryRunningOperation: Check if any operation is running (if not idle, another operation cannot start)
  • POST /im/types/Command/instances/actions/abort: Abort running/pending commands
  • POST /im/types/Command/instances/actions/clear: Archive completed/failed commands
  • POST /im/types/Command/instances/actions/retry: Retry failed commands

Pod Affinity

/im/ requests that relate to a running operation must be served by the same pod that started the operation.
PFMP deploys 2 block-legacy-gateway pods, without pod affinity a request could land on the wrong pod.
For example,querying progress of an install on pod 2 returns “idle” even though the install is running on pod 1.
Version 4.x (4.5 and later): Use the LEGACYGWCOOKIE cookie to pin all /im/ requests to the same pod. For more information, see the How to use the LEGACYGWCOOKIE cookie article.
Version 5.x: All /im/ requests are routed to the same pod by default; no cookie is needed.

PowerFlex Installation Manager operations: Configuration, Phases, and Management

Configuration JSON

All /im/ operations that act on the cluster require a configuration JSON as the request body.
This JSON describes the full cluster topology: MDM nodes, SDS or SDC or SDT or SDR components, protection domains, storage pools, node credentials, and security settings.

The configuration JSON is obtained by calling:
POST /im/types/Configuration/instances Content-Type: application/json { "mdmIps": ["10.1.0.1", "10.1.0.2"], "mdmUser": "admin", "mdmPassword": "<any_string>", "securityConfiguration": { "allowNonSecureCommunicationWithMdm": true, "allowNonSecureCommunicationWithLia": true, "disableNonMgmtComponentsAuth": false } }

Alternatively, for install operations, the configuration can be generated from a CSV file:

POST /im/types/Configuration/instances/actions/parseFromCSV Content-Type: multipart/form-data file=@config.csv

This queries the MDM and returns the full cluster Configuration JSON. The returned JSON is then used as the body of operation requests (for example, install, upgrade, liaRunOsPatching), with minor modifications depending on the operation.

Note:

  • The mdmUser and mdmPassword fields must be present in the request body (non-null), but their values are ignored. The gateway connects to MDM using mTLS (mutual TLS) and does not use these credentials. Any non-empty string value is acceptable.
  • Passwords (for example, liaPassword, mdmPassword) are returned as null for security. They must be filled in before sending to an operation.
    The mdmUser field must not be null.
    For install operations, liaPassword is mandatory (used until mTLS connection is established).

Operation phases

Each operation is divided into an ordered sequence of phases. Within each phase, individual commands execute on target nodes (in parallel where possible).

Operation Phases
install query -> upload -> install -> configure
upgrade query -> upload -> install
osPatching validate -> execute
securityBootstrap configureSecurity
resetManagementTrust configureSecurity
collectLogs query

Command states

Within each phase, individual commands execute on specific nodes. Each command has a state:

State Description
pending Queued, waiting to execute
running Currently executing on a target node
completed Finished successfully
failed Finished with error
aborted Was aborted by user

Command management APIs

Action API Description
List GET /im/types/Command/instances Returns all commands grouped by node, with their states and messages
Abort POST /im/…/actions/abort Aborts pending and running commands. Optional commandID to abort a specific command.
Clear POST /im/…/actions/clear Archives all finished commands (removes them from the active list). Must be called after an operation ends to allow new operations.
Retry POST /im/…/actions/retry Re-queues failed/aborted commands in the current phase. Optional commandID parameter to retry a specific command. Optional force parameter to retry even completed commands.

Note

  • Retry works for all operations (install, upgrade, uninstall, osPatching, etc.) - it re-queues failed/aborted commands in the current phase.

  • For upgrade: The operation stores a configurationBeforeUpgradeRetries snapshot so that retry can correctly re-evaluate the state.

  • For install: Retry has special handling for the query phase – if the query phase fails, retry marks all commands as failed first, then re-queues them.

For later phases (upload, install, configure), retry re-queues failed commands as usual, but in practice retrying the install phase may fail if components are already partially installed on some nodes.

  • For other operations (osPatching, securityBootstrap, etc.): retry re-queues failed commands as usual.
  • Before retrying, the operation state should typically be cleared first (abort + clear pending commands), then retry the failed ones.
