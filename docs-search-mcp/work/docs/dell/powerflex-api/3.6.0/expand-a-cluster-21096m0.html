Expand a cluster

Overview

The workflow expands an existing PowerFlex cluster by submitting a complete cluster topology to the Installation Manager.

The Installation Manager compares the submitted topology with the existing cluster configuration and installs only the newly added resources. The operation is asynchronous and must be monitored until it completes.

Purpose

The expand a cluster workflow allows administrators to add one or more storage nodes to an existing PowerFlex cluster.

The workflow performs prerequisite validation, verifies service readiness, submits the updated cluster configuration to the Installation Manager (IM), monitors deployment progress, and validates the successful completion of the workflow.

Prerequisites

Before starting the expand a workflow cluster, ensure the following:

  • There are valid PowerFlex Manager credentials available.
  • An authentication token is acquired.
  • There are no active vtree migrations running.
  • The Lifecycle Management (ALCM) service is healthy and available.
  • The target protection domain exists.
  • There are no conflicting deployment or upgrade jobs are currently running.
  • The configuration details for new nodes are available.

Workflow phases

Phase 1: Precheck

1.1 Validate authentication by running:

POST /rest/v1/tokens

Purpose:

  • Acquires a bearer token for all the subsequent requests.

1.2 Validate no active Vtree migrations are in progress by running:

GET /rest/v1/mirror-vtrees

Purpose: Verifies that no migration operations are currently active.

Failure condition:

  • Migration exists.

Result:

  • Workflow is blocked until migration completes.

1.3 Validate life cycle management readiness by running:

GET /app-ready?services=alcm

Purpose:

  • Verifies the Installation Manager services are operational.

Failure condition:

  • Service is unavailable.

Result:

  • Workflow is blocked.

1.4 Retrieve protection domains by running:

GET /api/types/ProtectionDomain/instances

Purpose:

  • Loads available protection domains and validates the target placement.

Phase 2: Initiation

2.1 Check existing deployment jobs by running:

POST /Api/V1/ui/jobs/getjoblist

Purpose: Verifies that no deployment or upgrade jobs are running.

Failure Condition

  • An active job is detected.

Result

  • You are warned that the workflow is prevented from starting.

2.2 Upload the required PowerFlex core RPM bundles to the Installation Manager only once per bundle by running:

     -H "Authorization: Bearer $MNO_TOKEN" \
     -F "file=@</path/to/core-rpms-or-bundle.rpm>" \
     "https://<PFMP_IP>/im/types/installationPackages/instances/actions/uploadPackages"

Purpose:

  • Expands a cluster.

2.3 Upload the CSV topology file with the new nodes by running:

     -H "Authorization: Bearer $MNO_TOKEN" \
     -F "file=@</path/to/topology.csv>" \
     "https://<PFMP_IP>/im/types/Configuration/instances/actions/parseFromCSV"

Purpose:

  • Prepares the CSV file with the additional nodes.

Result:

  • The response is the parsed configuration JSON that you will pass into the installation call below (<PREPARED_CSV_DICT_JSON>)in step 2.4.

2.4 Upload the CSV file and ensure it passes the validation checks by running:

     -H "Authorization: Bearer $MNO_TOKEN" \
     -H "Content-Type: application/json" \
     -X POST \
     "https://<PFMP_IP>/im/types/Configuration/actions/install?runAllPhases=true&clearProcess=true&noSecurityBootstrap=false&enableDeviceHardwareChecks=true&forceDevic
   eTakeover=true" \
     -d '<PREPARED_CSV_DICT_JSON>'

Note:

  • Enable the device takeover command only if the target disks were previously in use by a PowerFlex cluster.

  • Replace <PFMP_IP>, the file paths, and (<PREPARED_CSV_DICT_JSON>)with the specific values for your environment.

  • (<PREPARED_CSV_DICT_JSON>)is typically the JSON payload returned by theparseFromCSV API call, either unchanged or with the minimal modifications as you require.

Phase 3: Run

3.1 Run the installation operation by running:

POST /im/types/Configuration/actions/install

The Installation Manager completes the following tasks as part of the installation operation:

  1. Compares the submitted topology to the current topology.
  2. Identifies any new nodes.
  3. Performs hardware validation.
  4. Configures security trust.
  5. Claims devices.
  6. Expands the cluster.

Expected response:

202 Accepted

The workflow continues asynchronously.

Phase 4: Monitor

4.1 Monitor active jobs by running:

GET /pfblock/ps/http/jobs/count

Purpose

Determines whether the workflow is still running.

Status

> 0 = Running
0 = Complete

4.2 Monitor workflow progress

GET /pfblock/ps/jetty/observe

Purpose

Streams step-level workflow updates.

Returns

  • Current phase
  • Current step
  • Status
  • Percent complete

4.3 Monitor critical alerts by running:

GET /rest/v1/alerts

Purpose

Detect deployment-related critical conditions.

Failure condition

  • Active critical alert detected.

4.4 Monitor events by running:

GET /rest/v1/events

Purpose

  • Detects success and failure events.
  • Captures workflow completion messages.

Phase 5: Post-process

5.1 Update cluster inventory

Following successful completion:

  • New storage nodes are registered.
  • Devices are assigned to the specified protection domain.
  • Storage pools are updated.
  • Cluster topology reflects newly added resources.

Phase 6: Validate

6.1 Validate workflow completion

Perform the following validation checks:

  • Job count equals 0.
  • No active critical alerts exist.
  • Successful completion event recorded.
  • New storage nodes visible in cluster inventory.
  • Protection domain membership confirmed.
  • Storage devices operational.

Expected outcome

Upon successful completion:

  • The requested storage node(s) are added to the existing PowerFlex cluster.
  • The Installation Manager reports successful completion.
  • There are no active critical alerts.
  • New resources are available for normal operation.
  • The cluster topology reflects the updated configuration.

Error handling

An active migration is detected

Cause

An existing vtree migration is currently in progress.

User impact

The cluster expansion cannot start.

Recovery

Wait for the migration to complete and retry the workflow.

Returned status

Workflow Blocked

A life cycle management (ALCM) service is unavailable

Cause

The Installation Manager service is unavailable.

User impact

The configuration cannot be submitted.

Recovery

Restore the service health and retry the workflow.

Returned status

Service Unavailable

An existing deployment job is running

Cause

Another deployment or upgrade workflow is already running.

User impact

The expand operation is denied.

Recovery

Wait for the active job to complete and rerun the workflow.

Returned status

Request Blocked

A critical alert is generated

Cause

A deployment issue detected during execution.

User impact

The workflow may not complete successfully.

Recovery

Review the alert details and remediate before retrying.

Returned status

Warning
or
Failed Deployment

An Installation Manager failure

Cause

A configuration, network, hardware, or deployment failure.

User impact

A cluster expansion remains incomplete.

Recovery

Review the Installation Manager logs using the transaction ID (x-id) and rerun the workflow after corrective actions are complete.

Returned status

Failed
