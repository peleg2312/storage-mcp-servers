What’s New in the PowerMax REST API with Unisphere 10.3

October 15th, 2025

|

Read Time: 9 minutes

Paul Martin

The PowerMax REST API is a key component of Dell's Unisphere for PowerMax management software suite, offering a comprehensive and programmable interface for managing PowerMax storage arrays. Built on RESTful principles, it allows users to perform a wide range of operations—such as provisioning storage, monitoring performance, managing volumes, and configuring replication—using standard HTTP methods. It is a component of Unisphere for PowerMax management application thar every PowerMax user will have in their environment.

The PowerMax API supports secure authentication, versioning, and detailed error reporting, making it ideal for integration with automation frameworks and orchestration tools. As part of Unisphere, it benefits from centralized management capabilities and consistent user experience with the UI.

Unisphere for PowerMax OS 10.3 has just been released and supports new functionality and enhancements to the API.

Upgrading Unisphere for PowerMax to 10.3 will provide new functionality and compatibility to previous versions of the API for N-2 releases.  To check the version of API supported by a Unisphere instance, you can issue a GET call to https://unisphere:8443/univmax/restapi/version, which returns the supported API versions in the current release.

{
   "version": "T10.3.0.764",
   "api_version": "103",
   "supported_api_versions": [
     "103",
     "102",
     "101"
   ]
 }

If your scripts or applications are already using a supported version of PyU4V or API calls targeting compatible Unisphere REST endpoints, no immediate changes are required following an upgrade. This gives you time to evaluate changes required (usually just update version in your scripts) and build workflows for new functionality in the newer API calls.

If you are using our Python SDK PyU4V, a new version of PyU4V has also been released and is available on Python Package Index installable via PyPI using:

pip install PyU4V --upgrade

It’s important with every release to check the change log to ensure you are not using any depreciated functions or endpoints.  The REST API Changelog, which is easily accessible from the https://developer.dell.com/apis/4458/versions/10.3 documentation site, details anything that has been added or removed under What’s New section. I will give the highlight reel in the remainder of this post.  

It’s also important to check the PyU4V change log if using the SDK for any changes as occasionally some functions do get depreciated.

Major improvements

The biggest change in 10.3 is the introduction of a new /settings API resource that consolidates settings management endpoints and adds some new ones. Existing endpoints under /system will move to /settings, and new ones will be added. Scripts using the old endpoints should be updated accordingly. Utilizing these endpoints can reduce the standup and configuration of a Unisphere for PowerMax system from hours to seconds and is repeatable every time across all systems supporting the calls. 

All of the endpoints under /settings are designed to be idempotent, which will make them easier to integrate with ITSM tools like Ansible/Terraform etc. Idempotent simply means that they will only affect change when needed and won’t fail if something is already set. Since the endpoints are idempotent, implementing them directly with the URI module from Ansible makes them consumable prior to us releasing any new modules. The new endpoints are as follows. 

SERVICE REGISTRATION and Performance registration Calls

https://ipaddress:8443/univmax/restapi/103/settings/registration/performance GET/POST
https://ipaddress:8443/univmax/restapi/103/settings/registration/scg        GET/POST/DELETE
https://ipaddress:8443/univmax/restapi/103/settings/registration/scg/server_cert GET/PUT
https://ipaddress:8443/univmax/restapi/103/settings/registration/cloudiq GET/PUT

Security and access control API Calls

https://ipaddress:8443/univmax/restapi/103/settings/access_control/authentication PUT/GET
https://ipaddress:8443/univmax/restapi/103/settings/symmetrix/{symmetrixId}/access_control/host_access GET/POST/DEL
https://ipaddress:8443/univmax/restapi/103/settings/symmetrix/{symmetrixId}/access_control/authorization_rule GET/POST/PUT

NOTE: Some of the service registration and security API calls will require the user to supply the security certificate from the service being configured. These certificates need to be transformed into base64 encoded certificates sent as string values in the JSON payloads to the API. The documentation provides examples of how to do this with python- and Linux-based tools.  

Configure Alert Notification Targets EMAIL/SNMP/Syslog Targets

https://ipaddress:8443/univmax/restapi/103/settings/alert/notification      GET/POST 

Performance Thresholds Alerts 

https://ipaddress:8443/univmax/restapi/103/settings/alert/performance_threshold GET/PUT update global threshold alerts for performance alerting.

NOTE: Payloads can accept a subset of key value pairs, so you create a custom payload with only those of interest to your organizations’ needs.

Setup Notifications – where alerts are sent (email/syslog/snmp)

https://ipaddress:8443/univmax/restapi/103/settings/symmetrix/{symmetrixId}/alert/notification GET/PUT 

Unisphere Alert Policies

https://ipaddress:8443/univmax/restapi/103/settings/symmetrix/{symmetrixId}/alert/alert_policy GET/PUT
https://ipaddress:8443/univmax/restapi/103/settings/symmetrix/{symmetrixId}/alert/system_threshold GET/PUT

A sample playbook for configuring alerting targets and setting performance thresholds can be found here. This is the same playbook I showed at Dell Technologies world this year for anyone in attendance.  Running this playbook will have set the referenced values for the base settings I want to configure.  This is not an exhaustive playbook but an example you can expand with additional calls and build more around it.

Say goodbye to RSI and forget all that clicking around in the UI. With these APIs, you can setup and audit your configuration at any time with relative ease.  Obviously, there is some upfront effort to build your library of payloads, or you can copy from an existing system that has been upgraded to 10.3. using the corresponding GET calls. In general, the output of a GET can be used as the payload for a subsequent POST or PUT, provided the GET contains the parameters you want to set.  

Further enhancements to our enhanced APIs

If you haven’t revisited the PowerMax REST API lately, now’s a great time to take another look.
The enhanced endpoints offer simpler, faster access to more data, enabling leaner code and more efficient workflows.

  • Less code to maintain
  • Lower overhead on your management server
  • Faster response times
  • Works across all PowerMax models on supported Unisphere versions — no dependency on PowerMax OS.

I covered this in more detail in an earlier post — check it out [here]. 

These improvements are a big win for automation and integration. If you're building tooling or dashboards, this is well worth investing some time up front to streamline your operations. We’ve added more endpoints to give full coverage on your PowerMax arrays, giving access to your full array configuration via just a few API calls.

Addition of the following collection endpoints: 

  • Directors
  • Ports
  • Ip Routes
  • Ip Interfaces
  • RDF Groups
  • Port Groups
  • Masking Views
  • Hosts
  • Initiators

Enhanced Performance API – further enhancements

In addition to the new enhanced API calls introduced in this release, the existing performance API calls in the enhanced section of the API have been expanded. New query filter options allow for a longer time range to be returned for the request instead of just retrieving the last 5 minutes for each category.

Users can specify ?filter=time_range = X where x is the number of hours of data for the API to return.   You can request up to 24 hours of data. An example is below.

https://unisphere:8443/univmax/rest/v1/systems/{id}/performance-categories/{category}?filter=time_range eq 1

The returned JSON will include all metric instances at the 5-minute intervals for each component in the time range. This makes it easy to get data for longer periods with just a single call.

Not only that, but users can now also retrieve the maximum measured values in each of the 5-minute intervals by specifying another filter, data_format eq Maximum. It’s worth noting that you do need to have real time metrics enabled as the maximum is extracted from the 5 second intervals measured in the real time stats.

https://unisphere:8443/univmax/rest/v1/systems/{{v4SystemId}}/performance-categories/Board?filter=data_format eq Maximum

What This Means for You

  • Efficiency: You can now retrieve longer performance histories with a single API call.
  • Granularity: With data_format eq Maximum, you get peak values per interval, which is useful for identifying performance spikes.
  • Flexibility: These filters allow for more tailored queries depending on your monitoring or reporting needs.

One last piece of functionality to note, the enhanced volume API has a new key value for volume_host_paths. This is a great alternative way of retrieving the host lun address for volumes. In the example below, I am selecting the consistent_lun_address from volume_host_paths sub metadata. This is the host visible address for every masked volume on the system. This is a much more efficient call than the masking view connections call in the legacy API call, so if you are gathering this information, this is the best way to do it.  Note that you can also filter by masking view; I’m using a shotgun approach in the example, however we recommend you tone it to what you actually need.

https://unisphere:8443/univmax/rest/v1/systems/000120001646/volumes?select=volume_host_paths.consistent_lun_address&filter=num_of_masking_views ge 1

NOTE: This is not an exhaustive list of new API updates. Be sure to check the change log for the full list.

With each release, we enhance the server infrastructure behind our API to improve efficiency and performance. These updates occur seamlessly during upgrades without requiring any code changes. If you have questions, please open a discussion on the PyU4V GitHub, and we’ll respond promptly.

Managing your SRDF landscape just got easier with Unisphere 10.2

Unisphere 10.2 has just been released and there are more than a few new features to sink your teeth into.  However, I want to just focus in on and highlight a new dashboard available in the Data Protection section of Unisphere for managing your SRDF environments whether they are Synchronous, Asynchronous Metro, or MetroDR environments.

As part of the AIOps Predictive and Prescriptive Remediation initiative, Unisphere for PowerMax provides an overall view of the replication status of all storage groups for the array. This view provides a visual and interactive means of monitoring the replication from the viewpoint of an application. The focus is on providing users with sufficient information about the storage assets (the storage group and its configured replication solution) so that they can make informed decisions more quickly, and without needing to collate information from Unisphere for PowerMax.

The example below shows how to access this new dashboard. Note the traffic light system to quickly gauge if there are any issues in the SRDF setups. Storage groups are filtered by their operating state. My example is simple and only shows a single SRDF protected storage group, but in customer environments there could be hundreds or thousands, and the ability to categorize by operational state is a huge time saver. 

Note the SRDF_Blog_SG storage group is showing in a warning state due to the replication being suspended. 

The SRDF Storage Group details view provides you with a high-level overview of the SRDF status of a storage group will greatly improve your experience with HA/DR replication solutions. 

Clicking on a storage group displays a high-level topology diagram of the protection as shown below.

 

The high-level diagram helps to visualize the components that make up the replication configuration. From this view, you can quickly understand any current issues affecting an SRDF storage group that could impact its ability to replicate data. Clicking on any of the arrays in the configuration brings you into the SRDF Storage Group details view from the selected arrays perspective as shown below.

Any issues with the configuration display in the Overview tab in the bottom of the screen. Typical problems and criticality are listed below. The example above shows that SRDF group 2 has been suspended on array 105.
 

By clicking  the Data Protection tab, I can quickly manage the SRDF connection for the storage group. 

Clicking Establish removes the warning state.  

The SRDF Storage Group details view provides specific warnings and help for several issues that may impact the performance of a user's replication configuration.

The Critical state is determined if any of the following are true:

  • All initiators that are used in a host/host group for masking view are not logged in.
  • All initiators that are used in a host/host group for associated masking view are not on fabric.
  • All front end ports in a port group for masking view are offline.
  • All SRDF ports that are used in the associated SRDF group are offline.
  • The remote storage group in an SRDF/A configuration is more than 99 cycles behind the local storage group.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the Partitioned state.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the Transmit Idle state.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the Failed state.
     

The Warning state is determined if any of the following are true:

  • Some of the initiators that are used in a host/host group for associated masking view are not logged in.
  • Some of the initiators that are used in a host/host group for associated masking view are not on fabric.
  • Some of the front end ports in a port group are offline.
  • The remote storage group in an SRDF/A configuration is more than three cycles behind and fewer than 100 cycles behind the local storage group.
  • The storage group is protected by Metro but does not have a vWitness configured.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the Suspended state.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the Split state.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the Failed Over state.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the R1 updated state.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the R1 update in progress state.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the Unknown state.
  • The SRDF state of any SRDF pair in the SRDF Storage Group is in the Invalid state.
  • The DSE Pool is active for the SRDF group.
     

If you are unfamiliar with any of the states described above or need a refresher, see the latest SRDF Family CLI User Guide available from the Dell Support Site.

The tables in the Storage Group Status details view help the storage admin to identify quickly which components need action and quickly resolve issues with minimum fuss. Personally, I think the developers have done a smashing job here and will save you a lot of clicking and switching between views. Note there is no hardware requirement to take advantage of this feature, simply upgrading your system to Unisphere 10.2 provides this functionality to all supported VMAX and PowerMax arrays.
